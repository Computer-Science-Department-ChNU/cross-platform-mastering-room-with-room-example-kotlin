.About this lecture
--
In this lecture we add a local SQLite database to a Kotlin Multiplatform (KMP) project that targets *Android*, *iOS* and *Desktop (JVM)*, using the Jetpack *Room* library. The whole data layer -- entities, DAOs, the database class, relationships and migrations -- lives in `commonMain` and is shared by all three platforms. Only a few lines that decide _where the database file lives_ are platform-specific.

The material follows the official documentation on https://developer.android.com[developer.android.com] (Room and Kotlin Multiplatform guides) as of November 2026.
--

== Learning goals

After this lecture you should be able to:

* explain what Room is, which parts it consists of and how it works in KMP;
* configure Gradle (version catalog, KSP, Room plugin) for Android, iOS and Desktop;
* declare entities, DAOs and the database class in common code and create the database on every platform;
* implement CRUD operations and observe data reactively with `Flow`;
* model one-to-one, one-to-many, many-to-many and nested relationships;
* evolve the schema with automated and manual migrations and test them;
* avoid the most common mistakes (missing `suspend`, wrong KSP configuration, lost schema files, ...).

== Which Room? (Room 2.x vs Room 3.x)

Before writing any code it is important to know that there are currently *two* major lines of Room:

[cols="1,2,2",options="header"]
|===
| | Room 2.x (`androidx.room`) | Room 3.x (`androidx.room3`)
| Status (Nov 2026) | Maintenance mode -- bug fixes only | *Current*. Latest stable `{room-version}`, `3.1.0` in alpha
| Maven group / artifacts | `androidx.room:room-runtime` | `androidx.room3:room3-runtime`
| Gradle plugin / extension | `androidx.room` / `room { }` | `androidx.room3` / `room3 { }`
| KMP support | Android, iOS, JVM (since 2.7) | Android, iOS, JVM, *JS and WasmJS*
| Code generation | Java or Kotlin; KAPT, Java AP or KSP | *Kotlin only, KSP only*
| `SupportSQLite` / `Cursor` APIs | Available (Android) | *Removed* -- driver APIs (`SQLiteConnection`) only
| DAO functions | Blocking allowed on Android | Must be `suspend` (or return `Flow`/custom reactive type)
| Type converters | `@TypeConverter(s)` | `@ColumnTypeConverter(s)`
| LiveData / RxJava / Paging | Built in | Via `@DaoReturnTypeConverters` + extra artifacts
|===

This lecture uses *Room 3*, because it is the version developed for KMP. Most tutorials on the Internet were written for Room 2 -- the table above (and <<room2-to-room3>>) will help you translate them.

NOTE: The concepts (entity, DAO, database, relationships, migrations) are *identical* in both versions. Mostly the package names and a few APIs differ.

== Room architecture in a nutshell

Room is an abstraction layer over SQLite. It checks your SQL *at compile time*, maps rows to Kotlin objects, and turns queries into observable ``Flow``s.

----
          UI (Compose / SwiftUI)
                   │
             ViewModel / Repository                   commonMain
                   │
   ┌───────────────┼────────────────────────┐
   │  @Database AppDatabase                 │
   │      ├── @Dao TaskDao   ── @Entity TaskEntity
   │      └── @Dao ...       ── @Entity ...  │
   └───────────────┬────────────────────────┘
                   │  SQLiteDriver (BundledSQLiteDriver)
                   ▼
            SQLite database file   (path is platform-specific)
----

[horizontal]
Entity:: a class annotated with `@Entity` -- one table in the database.
DAO:: (Data Access Object) an interface annotated with `@Dao` -- functions that read and write data. Room generates the implementation.
Database:: an abstract class annotated with `@Database` -- the main access point; lists entities and exposes DAOs.
Driver:: an `androidx.sqlite.SQLiteDriver` implementation that actually opens connections to SQLite. In KMP we use `BundledSQLiteDriver`.

WARNING: Setting `schemaDirectory` is *required* when the Room Gradle plugin is applied. The generated `schemas/` folder is the history of your database. *Commit it to version control* -- automated migrations and migration tests depend on it.

== The basics: Entity, DAO, Database

All code in this chapter lives in `commonMain`. We build a small *To-Do* app.

=== Entity

An entity is a table. Every property becomes a column; one or more columns form the primary key.

.commonMain/kotlin/data/TaskEntity.kt
[source,kotlin]
----
import androidx.room3.ColumnInfo
import androidx.room3.Entity
import androidx.room3.Ignore
import androidx.room3.Index
import androidx.room3.PrimaryKey

@Entity(
    tableName = "tasks",                          // default would be "TaskEntity"
    indices = [Index(value = ["is_done"])]        // speeds up WHERE is_done = ?
)
data class TaskEntity(
    @PrimaryKey(autoGenerate = true)
    val id: Long = 0,                             // 0 = "let SQLite assign the id"

    val title: String,                            // NOT NULL column

    val description: String? = null,              // nullable -> NULL allowed

    @ColumnInfo(name = "is_done")
    val isDone: Boolean = false,                  // stored as INTEGER 0/1

    @ColumnInfo(name = "created_at")
    val createdAt: Long,                          // epoch millis

    @Ignore
    val isSelected: Boolean = false               // UI-only, not stored
)
----

Main entity annotations:

[cols="1,3",options="header"]
|===
| Annotation / property | Meaning
| `@Entity(tableName = ...)` | Marks the class as a table; optional custom table name.
| `@PrimaryKey(autoGenerate = true)` | Primary key; `autoGenerate` lets SQLite assign ids.
| `@Entity(primaryKeys = ["a", "b"])` | Composite primary key.
| `@ColumnInfo(name = ..., defaultValue = ...)` | Custom column name / SQL default value (important for migrations!).
| `@Ignore` | Property is not persisted. In a constructor it needs a default value.
| `indices = [Index(..., unique = true)]` | Index / unique constraint.
| `foreignKeys = [ForeignKey(...)]` | Referential integrity, see <<foreign-keys>>.
| `@Embedded` | Flattens another class's properties into this table, see <<embedded>>.
| `@Fts4`, `@Fts5` (Room 3) | Full-text-search tables.
|===

NOTE: Table and column names in SQLite are *case-insensitive*. Room supports primitive types, `String`, `ByteArray`, enums (stored by name) and their nullable versions out of the box. Anything else needs a type converter (<<type-converters>>).

=== DAO -- Data Access Object

A DAO is an interface; Room generates the implementation at compile time and *verifies every SQL query against the schema*. A typo in a column name is a compile error, not a crash.

.commonMain/kotlin/data/TaskDao.kt
[source,kotlin]
----
import androidx.room3.*
import kotlinx.coroutines.flow.Flow

@Dao
interface TaskDao {

    // ---------- CREATE ----------
    @Insert
    suspend fun insert(task: TaskEntity): Long            // returns new rowId

    @Insert(onConflict = OnConflictStrategy.REPLACE)
    suspend fun insertAll(tasks: List<TaskEntity>): List<Long>

    // ---------- READ ----------
    @Query("SELECT * FROM tasks WHERE id = :id")
    suspend fun getById(id: Long): TaskEntity?            // null if not found

    @Query("SELECT * FROM tasks ORDER BY created_at DESC")
    fun observeAll(): Flow<List<TaskEntity>>              // NOT suspend - Flow

    @Query("SELECT * FROM tasks WHERE is_done = :done ORDER BY created_at DESC")
    fun observeByStatus(done: Boolean): Flow<List<TaskEntity>>

    @Query("SELECT * FROM tasks WHERE title LIKE '%' || :query || '%'")
    suspend fun search(query: String): List<TaskEntity>

    @Query("SELECT * FROM tasks WHERE id IN (:ids)")
    suspend fun getByIds(ids: List<Long>): List<TaskEntity>   // list is expanded

    @Query("SELECT COUNT(*) FROM tasks WHERE is_done = 0")
    fun observeActiveCount(): Flow<Int>

    // ---------- UPDATE ----------
    @Update
    suspend fun update(task: TaskEntity): Int             // rows updated (by PK)

    @Query("UPDATE tasks SET is_done = :done WHERE id = :id")
    suspend fun setDone(id: Long, done: Boolean): Int

    // ---------- INSERT or UPDATE ----------
    @Upsert
    suspend fun upsert(task: TaskEntity): Long            // -1 if it was an update

    // ---------- DELETE ----------
    @Delete
    suspend fun delete(task: TaskEntity): Int             // rows deleted (by PK)

    @Query("DELETE FROM tasks WHERE is_done = 1")
    suspend fun deleteCompleted(): Int
}
----

[cols="1,3",options="header"]
|===
| Annotation | What it does
| `@Insert` | Inserts the given entities. Single parameter -> can return the new `rowId` (`Long`); list -> `List<Long>`. `onConflict` = `ABORT` (default), `REPLACE`, `IGNORE`.
| `@Update` | Finds rows by *primary key* and updates them. Can return the number of affected rows. If no row has that key -- nothing happens.
| `@Delete` | Deletes rows by primary key. Can return the number of deleted rows.
| `@Upsert` | Insert, or update if the primary key already exists. Returns the new `rowId`, or `-1` when an existing row was updated. Prefer it over `REPLACE`, which actually _deletes_ the old row (and cascades!).
| `@Query("...")` | Any SQL. Parameters are bound with `:name`. Return types: entity, `List`, nullable single value, primitives, `Flow`, data classes with a subset of columns, `Pair`/`Triple`, `Map` (multimap).
| `@Transaction` | Runs the function in one transaction. Required for `@Relation` queries.
| `@RawQuery` | Query built at runtime (`RoomRawQuery`). Not verified at compile time -- use rarely.
|===

[IMPORTANT]
.Rules for DAO functions in KMP / Room 3
====
* Every one-shot function must be `suspend`. Blocking DAO functions are not allowed (in Room 2 only Android-only DAOs may be blocking).
* Observable queries return `Flow<T>` and are *not* `suspend`. Room re-runs the query and emits a new value every time one of the tables used in the query changes.
* `LiveData`, RxJava, Guava and Paging need extra artifacts and `@DaoReturnTypeConverters` (<<extras>>).
====

=== Database class

.commonMain/kotlin/data/AppDatabase.kt
[source,kotlin]
----
import androidx.room3.ConstructedBy
import androidx.room3.Database
import androidx.room3.RoomDatabase
import androidx.room3.RoomDatabaseConstructor

@Database(
    entities = [TaskEntity::class],
    version = 1,
    exportSchema = true                 // default; needed for migrations
)
@ConstructedBy(AppDatabaseConstructor::class)
abstract class AppDatabase : RoomDatabase() {
    abstract fun taskDao(): TaskDao
}

// Room's compiler generates the `actual` implementation for each platform.
@Suppress("KotlinNoActualForExpect")
expect object AppDatabaseConstructor : RoomDatabaseConstructor<AppDatabase> {
    override fun initialize(): AppDatabase
}
----

Why `@ConstructedBy`? On Android/JVM Room finds the generated `AppDatabase_Impl` class through reflection. Kotlin/Native (iOS) has no reflection, so in KMP you declare an `expect object` and Room's compiler writes the `actual` for every target. The IDE may warn "_Expected object has no actual declaration_" -- that is expected, hence the `@Suppress`.

=== Creating the database on each platform

The *only* platform-specific code is the database *builder* -- each platform stores files in a different place.

.androidMain/kotlin/data/Database.android.kt
[source,kotlin]
----
import android.content.Context
import androidx.room3.Room
import androidx.room3.RoomDatabase

fun getDatabaseBuilder(context: Context): RoomDatabase.Builder<AppDatabase> {
    val appContext = context.applicationContext
    val dbFile = appContext.getDatabasePath("app.db")
    return Room.databaseBuilder<AppDatabase>(
        context = appContext,
        name = dbFile.absolutePath
    )
}
----

.iosMain/kotlin/data/Database.ios.kt
[source,kotlin]
----
import androidx.room3.Room
import androidx.room3.RoomDatabase
import kotlinx.cinterop.ExperimentalForeignApi
import platform.Foundation.NSDocumentDirectory
import platform.Foundation.NSFileManager
import platform.Foundation.NSUserDomainMask

fun getDatabaseBuilder(): RoomDatabase.Builder<AppDatabase> {
    val dbFilePath = documentDirectory() + "/app.db"
    return Room.databaseBuilder<AppDatabase>(name = dbFilePath)
}

@OptIn(ExperimentalForeignApi::class)
private fun documentDirectory(): String {
    val documentDirectory = NSFileManager.defaultManager.URLForDirectory(
        directory = NSDocumentDirectory,
        inDomain = NSUserDomainMask,
        appropriateForURL = null,
        create = false,
        error = null,
    )
    return requireNotNull(documentDirectory?.path)
}
----

.desktopMain/kotlin/data/Database.desktop.kt
[source,kotlin]
----
import androidx.room3.Room
import androidx.room3.RoomDatabase
import java.io.File

fun getDatabaseBuilder(): RoomDatabase.Builder<AppDatabase> {
    val dbFile = File(appDataDir(), "app.db")
    return Room.databaseBuilder<AppDatabase>(name = dbFile.absolutePath)
}

// A persistent, per-user location (java.io.tmpdir may be cleared on reboot)
private fun appDataDir(): File {
    val os = System.getProperty("os.name").lowercase()
    val home = System.getProperty("user.home")
    val dir = when {
        "win" in os -> File(System.getenv("APPDATA") ?: home, "MyTodoApp")
        "mac" in os -> File(home, "Library/Application Support/MyTodoApp")
        else        -> File(home, ".local/share/MyTodoApp")
    }
    return dir.apply { mkdirs() }
}
----

TIP: The official sample uses `java.io.tmpdir` on Desktop for simplicity, but that directory may be cleared on reboot. Use a real application-data directory in production.

The rest of the configuration is shared:

.commonMain/kotlin/data/AppDatabase.kt (continued)
[source,kotlin]
----
import androidx.sqlite.driver.bundled.BundledSQLiteDriver
import kotlinx.coroutines.Dispatchers
import kotlinx.coroutines.IO

fun getRoomDatabase(
    builder: RoomDatabase.Builder<AppDatabase>
): AppDatabase {
    return builder
        .setDriver(BundledSQLiteDriver())          // same SQLite on all platforms
        .setQueryCoroutineContext(Dispatchers.IO)  // where queries run
        .build()
}
----

[NOTE]
====
* *`BundledSQLiteDriver`* (recommended) compiles SQLite from source and ships it with the app, so every platform uses the *same SQLite version and features* (e.g. all FTS versions, JSON functions).
* Alternatives that use the OS SQLite: `AndroidSQLiteDriver` (androidMain) and `NativeSQLiteDriver` (iosMain; requires `linkerOpts.add("-lsqlite3")` in the framework config).
* `setQueryCoroutineContext` replaces Android's `setQueryExecutor` (executors are JVM-only). Default is `Dispatchers.IO`.
====

==== Wiring it up -- one instance per app

Creating a `RoomDatabase` is expensive. Create it *once* and share it (singleton or dependency injection).

[source,kotlin]
----
// Android - e.g. in Application.onCreate()
val database = getRoomDatabase(getDatabaseBuilder(applicationContext))

// iOS - iosMain, called from MainViewController / Swift
fun createDatabase(): AppDatabase = getRoomDatabase(getDatabaseBuilder())

// Desktop - main()
fun main() = application {
    val database = remember { getRoomDatabase(getDatabaseBuilder()) }
    // ...
}
----

With *Koin* the typical pattern is a common module plus a platform module:

// iosMain and desktopMain

=== CRUD in practice: repository and ViewModel

.commonMain/kotlin/data/TaskRepository.kt
[source,kotlin]
----
import kotlin.time.Clock
import kotlin.time.ExperimentalTime

class TaskRepository(private val dao: TaskDao) {

    val tasks: Flow<List<TaskEntity>> = dao.observeAll()            // Read (observe)

    @OptIn(ExperimentalTime::class)
    suspend fun add(title: String, description: String? = null): Long =   // Create
        dao.insert(
            TaskEntity(
                title = title,
                description = description,
                createdAt = Clock.System.now().toEpochMilliseconds()
            )
        )

    suspend fun toggle(task: TaskEntity) =                           // Update
        dao.update(task.copy(isDone = !task.isDone))

    suspend fun rename(id: Long, newTitle: String) {                 // Read + Update
        val task = dao.getById(id) ?: return
        dao.update(task.copy(title = newTitle))
    }

    suspend fun remove(task: TaskEntity) = dao.delete(task)          // Delete

    suspend fun clearCompleted() = dao.deleteCompleted()
}
----

.commonMain/kotlin/ui/TasksViewModel.kt (androidx.lifecycle ViewModel is multiplatform)
[source,kotlin]
----
class TasksViewModel(private val repository: TaskRepository) : ViewModel() {

    val tasks: StateFlow<List<TaskEntity>> = repository.tasks
        .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), emptyList())

    fun add(title: String) = viewModelScope.launch { repository.add(title) }
    fun toggle(task: TaskEntity) = viewModelScope.launch { repository.toggle(task) }
    fun delete(task: TaskEntity) = viewModelScope.launch { repository.remove(task) }
}
----

Note the flow of data: `add()` inserts a row -> Room notices that table `tasks` changed -> `observeAll()` re-emits -> the `StateFlow` updates -> the UI recomposes. *You never refresh the list manually.*

NOTE: When the UI is written in SwiftUI, Kotlin `suspend` functions are visible in Swift as `async` functions (Kotlin 2.x / Swift export) or completion-handler functions. For collecting `Flow` in Swift, libraries like *SKIE* or *KMP-NativeCoroutines* are commonly used. With Compose Multiplatform no extra work is needed.

[#type-converters]
=== Type converters

SQLite only knows `INTEGER`, `REAL`, `TEXT`, `BLOB` and `NULL`. To store other types (dates, UUIDs, lists, ...) you write a pair of conversion functions. In Room 3 they are called *column type converters*.

[source,kotlin]
----
import androidx.room3.ColumnTypeConverter
import kotlinx.datetime.LocalDate

object Converters {
    @ColumnTypeConverter
    fun localDateToString(date: LocalDate?): String? = date?.toString()   // "2026-11-17"

    @ColumnTypeConverter
    fun stringToLocalDate(value: String?): LocalDate? = value?.let(LocalDate::parse)
}

@Database(entities = [TaskEntity::class], version = 1)
@ColumnTypeConverters(Converters::class)      // applies to the whole database
@ConstructedBy(AppDatabaseConstructor::class)
abstract class AppDatabase : RoomDatabase() { /* ... */ }
----

* `@ColumnTypeConverters` may also be put on a single entity, DAO or property to limit its scope.
* If a converter needs dependencies (e.g. a JSON serializer), annotate it with `@ProvidedColumnTypeConverter` and pass an instance with `builder.addColumnTypeConverter(instance)`.
* Enums have a built-in converter; Room 3.1 adds a built-in converter for `kotlin.uuid.Uuid`.
* Room 2 names: `@TypeConverter`, `@TypeConverters`, `@ProvidedTypeConverter`, `addTypeConverter`.

TIP: Avoid storing lists as JSON strings in one column when you need to search or join on the values -- that is a sign you need a separate table and a relationship.

== Relationships

=== Why no object references?

In an ORM like Hibernate you could write `book.author.name` and the library would lazily load the author. *Room deliberately forbids entities from referencing each other*:

* lazy loading usually happens on the UI thread -- a 5 ms query already risks a dropped frame (a frame is ~16 ms);
* eager loading of everything wastes memory on data you never show;
* sharing one model between DB and UI does not scale.

Instead, entities reference each other by *key columns*, and you explicitly describe *what you want to load together* -- either with a *result data class* using `@Embedded` + `@Relation`, or with a *multimap* query (`Map<A, List<B>>`).

The examples below use a music app (as in the official docs):

----
 User 1 ──── 1 Library            one-to-one
 User 1 ──── N Playlist           one-to-many
 Playlist N ── M Song             many-to-many (via PlaylistSongCrossRef)
 User → Playlists → Songs         nested
----

[#embedded]
=== Embedded objects (`@Embedded`)

Not a relationship between tables, but a way to group columns. The embedded class's properties become columns of the *same* table.

[source,kotlin]
----
data class Address(
    val street: String?,
    val city: String?,
    @ColumnInfo(name = "post_code") val postCode: Int
)

@Entity
data class User(
    @PrimaryKey val id: Long,
    val firstName: String,
    @Embedded val address: Address?                     // -> street, city, post_code
    // @Embedded(prefix = "home_") val home: Address    // -> home_street, ...
)
----

Table `User` gets the columns `id`, `firstName`, `street`, `city`, `post_code`. If an entity embeds the same type twice, use `prefix` to keep column names unique. `@Embedded` is also the building block for `@Relation` classes below.

[#foreign-keys]
=== Foreign keys -- data integrity

`@Relation` only describes how to *read* related data. To let SQLite *guarantee* that a child row always points to an existing parent, declare a foreign key:

[source,kotlin]
----
@Entity(
    foreignKeys = [
        ForeignKey(
            entity = User::class,
            parentColumns = ["userId"],
            childColumns = ["userCreatorId"],
            onDelete = ForeignKey.CASCADE,     // delete user -> delete their playlists
            onUpdate = ForeignKey.CASCADE
        )
    ],
    indices = [Index("userCreatorId")]          // always index FK columns!
)
data class Playlist(
    @PrimaryKey(autoGenerate = true) val playlistId: Long = 0,
    val userCreatorId: Long,
    val playlistName: String
)
----

* `onDelete`/`onUpdate` actions: `NO_ACTION` (default), `RESTRICT`, `SET_NULL`, `SET_DEFAULT`, `CASCADE`.
* Room warns at compile time if a foreign key column is not indexed (otherwise every parent change triggers a full table scan).
* Inserting a child with a non-existent parent throws `SQLiteException` (FOREIGN KEY constraint failed).
* Beware of `@Insert(onConflict = REPLACE)` on a parent: `REPLACE` deletes the old row first, which triggers `CASCADE` and *removes the children*. Use `@Upsert` or `@Update`.

=== One-to-one

Each user has exactly one library; each library belongs to exactly one user.

[source,kotlin]
----
@Entity
data class User(
    @PrimaryKey val userId: Long,
    val name: String,
    val age: Int
)

@Entity(indices = [Index(value = ["userOwnerId"], unique = true)])   // enforces 1:1
data class Library(
    @PrimaryKey val libraryId: Long,
    val userOwnerId: Long                     // references User.userId
)

// Result class - NOT an entity
data class UserAndLibrary(
    @Embedded val user: User,
    @Relation(
        parentColumns = ["userId"],           // column in the @Embedded parent
        entityColumns = ["userOwnerId"]       // matching column in the child
    )
    val library: Library?                     // nullable if a user may have no library
)

@Dao
interface UserDao {
    @Transaction
    @Query("SELECT * FROM User")
    suspend fun getUsersAndLibraries(): List<UserAndLibrary>

    @Transaction
    @Query("SELECT * FROM User WHERE userId = :id")
    fun observeUserAndLibrary(id: Long): Flow<UserAndLibrary?>
}
----

How it works: Room runs `SELECT * FROM User`, then a second query `SELECT * FROM Library WHERE userOwnerId IN (...)` and stitches the results together. Because there are *two* queries, the function must be annotated with `@Transaction` so both read a consistent snapshot.

=== One-to-many

A user creates many playlists; each playlist has exactly one creator. The *child* holds a column referring to the parent's key.

[source,kotlin]
----
@Entity
data class Playlist(
    @PrimaryKey val playlistId: Long,
    val userCreatorId: Long,                   // -> User.userId
    val playlistName: String
)

data class UserWithPlaylists(
    @Embedded val user: User,
    @Relation(
        parentColumns = ["userId"],
        entityColumns = ["userCreatorId"]
    )
    val playlists: List<Playlist>              // empty list if none
)

@Transaction
@Query("SELECT * FROM User")
suspend fun getUsersWithPlaylists(): List<UserWithPlaylists>
----

Composite keys (Room 3): list several columns; the order must match.

[source,kotlin]
----
@Relation(
    parentColumns = ["firstName", "lastName"],
    entityColumns = ["userFirstName", "userLastName"]
)
val playlists: List<Playlist>
----

TIP: You can load only some columns of the child: `@Relation(entity = Playlist::class, parentColumns = [...], entityColumns = [...]) val names: List<PlaylistName>` where `PlaylistName` is a small data class; or a single column via `projection = ["playlistName"]` with `List<String>`.

=== Many-to-many

A playlist contains many songs; a song can be in many playlists. This needs a third table -- a *cross-reference* (junction, associative) entity with the primary keys of both sides.

[source,kotlin]
----
@Entity
data class Song(
    @PrimaryKey val songId: Long,
    val songName: String,
    val artist: String
)

@Entity(
    primaryKeys = ["playlistId", "songId"],
    indices = [Index("songId")],
    foreignKeys = [
        ForeignKey(entity = Playlist::class, parentColumns = ["playlistId"],
                   childColumns = ["playlistId"], onDelete = ForeignKey.CASCADE),
        ForeignKey(entity = Song::class, parentColumns = ["songId"],
                   childColumns = ["songId"], onDelete = ForeignKey.CASCADE)
    ]
)
data class PlaylistSongCrossRef(
    val playlistId: Long,
    val songId: Long
)
----

The direction of the query decides which result class you write:

[source,kotlin]
----
// playlists -> their songs
data class PlaylistWithSongs(
    @Embedded val playlist: Playlist,
    @Relation(
        parentColumns = ["playlistId"],
        entityColumns = ["songId"],
        associateBy = Junction(PlaylistSongCrossRef::class)
    )
    val songs: List<Song>
)

// songs -> playlists that contain them
data class SongWithPlaylists(
    @Embedded val song: Song,
    @Relation(
        parentColumns = ["songId"],
        entityColumns = ["playlistId"],
        associateBy = Junction(PlaylistSongCrossRef::class)
    )
    val playlists: List<Playlist>
)

@Dao
interface MusicDao {
    @Insert suspend fun insertPlaylist(playlist: Playlist): Long
    @Insert suspend fun insertSongs(songs: List<Song>)
    @Insert(onConflict = OnConflictStrategy.IGNORE)
    suspend fun insertCrossRefs(refs: List<PlaylistSongCrossRef>)

    @Transaction
    @Query("SELECT * FROM Playlist")
    fun observePlaylistsWithSongs(): Flow<List<PlaylistWithSongs>>

    @Transaction
    @Query("SELECT * FROM Song")
    suspend fun getSongsWithPlaylists(): List<SongWithPlaylists>

    // Writing related data atomically: a DAO function with a body
    @Transaction
    suspend fun addSongToPlaylist(playlistId: Long, song: Song) {
        insertSongs(listOf(song))
        insertCrossRefs(listOf(PlaylistSongCrossRef(playlistId, song.songId)))
    }
}
----

NOTE: If the column names in the junction differ from those of the parent/child, set them in the `Junction(value = ..., parentColumns = [...], entityColumns = [...])` too.

=== Nested relationships

Load *all users, each with their playlists, each with its songs*. Model the relation between two tables first, then nest that class in another one.

[source,kotlin]
----
data class UserWithPlaylistsAndSongs(
    @Embedded val user: User,
    @Relation(
        entity = Playlist::class,                // the TABLE to query
        parentColumns = ["userId"],
        entityColumns = ["userCreatorId"]
    )
    val playlists: List<PlaylistWithSongs>      // a relation class, not an entity
)

@Transaction
@Query("SELECT * FROM User")
suspend fun getUsersWithPlaylistsAndSongs(): List<UserWithPlaylistsAndSongs>
----

When the list element is not itself an entity, you must name the table via `entity = ...`.

CAUTION: Nested relationships make Room run many queries and process a lot of data. Use as few levels of nesting as possible, and filter in the top-level `WHERE` clause.

=== Alternative: multimap return types

Instead of result classes, a DAO can return a `Map` directly from a `JOIN`. The official docs *recommend multimaps* unless you have a specific reason to use intermediate data classes.

[source,kotlin]
----
// one-to-many with a JOIN
@Query("""
    SELECT * FROM User
    JOIN Playlist ON User.userId = Playlist.userCreatorId
""")
suspend fun getUserPlaylists(): Map<User, List<Playlist>>

// aggregated value per key
@Query("""
    SELECT User.*, COUNT(Playlist.playlistId) AS playlist_count
    FROM User LEFT JOIN Playlist ON User.userId = Playlist.userCreatorId
    GROUP BY User.userId
""")
suspend fun getPlaylistCount(): Map<User, @MapColumn(columnName = "playlist_count") Int>
----

[cols="1,1",options="header"]
|===
| `@Relation` data class | Multimap (`Map<K, V>`)
| No SQL `JOIN` needed; Room runs several queries | One SQL query with `JOIN` -- you control filtering/sorting
| Reusable, named result types; easy nesting | Less boilerplate, no extra classes
| Needs `@Transaction` | Inner `JOIN` drops parents without children (use `LEFT JOIN`)
|===

[#migrations]
== Migrations

=== Why migrations?

Your app is installed on users' devices with a database of version *N*. A new release changes the entities -- version *N+1*. Room must transform the existing file *without losing data*. That transformation is a *migration*.

Workflow every time the schema changes:

. Change the entities / add new ones.
. *Increase* `version` in `@Database` (1 -> 2).
. Provide a migration path from every older version: *automated* (`@AutoMigration`) or *manual* (`Migration`).
. Build -- Room writes `schemas/.../2.json`. Commit it.
. Test the migration.

If Room opens a database with an old version and finds no path to the current one, it throws `IllegalStateException` (unless a destructive fallback is configured). If you change the schema but *forget* to bump the version, Room throws because the schema hash does not match.

=== Exported schemas

Each version is exported as JSON (location set with `room3 { schemaDirectory(...) }`):

----
shared/schemas/com.example.data.AppDatabase/
├── 1.json
├── 2.json
└── 3.json
----

The JSON contains every table's exact `createSql`, columns, indices and an `identityHash`. Automated migrations are generated by *diffing two of these files*, and `MigrationTestHelper` recreates old versions from them. *Losing these files = losing the ability to auto-migrate.*

=== Automated migrations

For most simple changes (new table, new column, new index), Room can generate the migration itself.

.Version 2: add a `priority` column
[source,kotlin]
----
@Entity(tableName = "tasks")
data class TaskEntity(
    @PrimaryKey(autoGenerate = true) val id: Long = 0,
    val title: String,
    val description: String? = null,
    @ColumnInfo(name = "is_done") val isDone: Boolean = false,
    @ColumnInfo(name = "created_at") val createdAt: Long,
    @ColumnInfo(defaultValue = "0") val priority: Int = 0          // NEW
)

@Database(
    entities = [TaskEntity::class],
    version = 2,                                                     // was 1
    autoMigrations = [
        AutoMigration(from = 1, to = 2)
    ]
)
@ConstructedBy(AppDatabaseConstructor::class)
abstract class AppDatabase : RoomDatabase() { /* ... */ }
----

IMPORTANT: A new `NOT NULL` column needs an SQL default (`@ColumnInfo(defaultValue = "0")`) -- otherwise existing rows have no value and the migration cannot be generated. The Kotlin default `= 0` is *not* an SQL default.

==== `AutoMigrationSpec` -- when Room needs a hint

If a change is ambiguous, Room fails *at compile time* and asks for a spec. Typical cases: renaming or deleting a table or column (a rename looks like "delete column A + add column B" -- data would be lost).

.Version 3: rename `description` -> `notes`, delete table `legacy_tags`
[source,kotlin]
----
@Database(
    entities = [TaskEntity::class],
    version = 3,
    autoMigrations = [
        AutoMigration(from = 1, to = 2),
        AutoMigration(from = 2, to = 3, spec = AppDatabase.Migration2To3::class)
    ]
)
@ConstructedBy(AppDatabaseConstructor::class)
abstract class AppDatabase : RoomDatabase() {
    abstract fun taskDao(): TaskDao

    @RenameColumn(tableName = "tasks", fromColumnName = "description", toColumnName = "notes")
    @DeleteTable(tableName = "legacy_tags")
    class Migration2To3 : AutoMigrationSpec {
        override suspend fun onPostMigrate(connection: SQLiteConnection) {
            // optional: runs after the generated migration, e.g. fix data
            connection.execSQL("UPDATE tasks SET notes = '' WHERE notes IS NULL")
        }
    }
}
----

Available spec annotations: `@RenameTable`, `@DeleteTable`, `@RenameColumn`, `@DeleteColumn` (repeatable). If the spec needs constructor arguments, mark it `@ProvidedAutoMigrationSpec` and register an instance with `builder.addAutoMigrationSpec(...)`.

=== Manual migrations

Use a manual migration when Room cannot know what to do -- e.g. splitting a table, changing a column's type, transforming data. You write SQL against a `SQLiteConnection` (Room 3 / KMP; Room 2 on Android used `SupportSQLiteDatabase`).

.Version 4: `priority` changes from INTEGER (0/1/2) to an enum stored as TEXT
[source,kotlin]
----
enum class Priority { LOW, MEDIUM, HIGH }       // enums are stored by name (TEXT)

// in TaskEntity:  val priority: Priority = Priority.LOW

import androidx.room3.migration.Migration
import androidx.sqlite.SQLiteConnection
import androidx.sqlite.execSQL

val MIGRATION_3_4 = object : Migration(3, 4) {
    override suspend fun migrate(connection: SQLiteConnection) {
        // SQLite cannot change a column type -> recreate the table
        // 1. create the new table (copy createSql from schemas/.../4.json!)
        connection.execSQL(
            "CREATE TABLE IF NOT EXISTS `tasks_new` (" +
            "`id` INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL, " +
            "`title` TEXT NOT NULL, `notes` TEXT, " +
            "`is_done` INTEGER NOT NULL, `created_at` INTEGER NOT NULL, " +
            "`priority` TEXT NOT NULL)"
        )
        // 2. copy & convert the data
        connection.execSQL(
            "INSERT INTO tasks_new (id, title, notes, is_done, created_at, priority) " +
            "SELECT id, title, notes, is_done, created_at, " +
            "CASE priority WHEN 2 THEN 'HIGH' WHEN 1 THEN 'MEDIUM' ELSE 'LOW' END " +
            "FROM tasks"
        )
        // 3. drop the old table and rename the new one
        connection.execSQL("DROP TABLE tasks")
        connection.execSQL("ALTER TABLE tasks_new RENAME TO tasks")
        // 4. recreate indices
        connection.execSQL("CREATE INDEX IF NOT EXISTS `index_tasks_is_done` ON `tasks` (`is_done`)")
    }
}
----

Register manual migrations on the builder (in common code):

[source,kotlin]
----
fun getRoomDatabase(builder: RoomDatabase.Builder<AppDatabase>): AppDatabase =
    builder
        .addMigrations(MIGRATION_3_4)          // auto migrations need no registration
        .setDriver(BundledSQLiteDriver())
        .setQueryCoroutineContext(Dispatchers.IO)
        .build()
----

[TIP]
====
* After the migration Room *validates* the resulting schema against the expected one. Any difference (a missing `NOT NULL`, a different default, a missing index) -> `IllegalStateException: Migration didn't properly handle ...`. The safest way to get exact SQL is to copy `createSql` from the exported JSON of the new version.
* Use full SQL strings in migrations, not constants shared with the rest of the code -- the migration must keep doing the same thing even when the code changes later.
* Auto and manual migrations can be mixed. If both exist for the same versions, *the manual one wins*.
* Room can chain migrations: 1->2->3->4. You do not need a migration from every version to the latest one, but you may add shortcuts (e.g. `Migration(1, 4)`) for speed.
====

=== Destructive fallback

When losing local data is acceptable (e.g. a pure cache that can be re-downloaded):

[source,kotlin]
----
builder
    .fallbackToDestructiveMigration(dropAllTables = true)          // any missing path
    // .fallbackToDestructiveMigrationFrom(dropAllTables = true, 1, 2)  // only from these versions
    // .fallbackToDestructiveMigrationOnDowngrade(dropAllTables = true) // only on downgrade
----

WARNING: This *deletes all data* in the user's database when a migration path is missing. Never use it for data the user created (notes, settings, purchases...) -- it silently hides forgotten migrations.

=== Testing migrations

Add the testing artifact. `MigrationTestHelper` creates a database of an old version from the exported schema, runs your migrations and validates the result.

.Desktop (JVM) test -- runs quickly without a device
[source,kotlin]
----
// build.gradle.kts:  sourceSets { val desktopTest by getting { dependencies {
//     implementation(libs.androidx.room3.testing); implementation(kotlin("test")) } } }

import androidx.room3.testing.MigrationTestHelper
import androidx.sqlite.driver.bundled.BundledSQLiteDriver
import java.nio.file.Files
import java.nio.file.Path
import kotlinx.coroutines.test.runTest

class MigrationTest {

    @get:org.junit.Rule
    val helper = MigrationTestHelper(
        schemaDirectoryPath = Path.of("schemas"),                // relative to module
        databasePath = Files.createTempDirectory("db").resolve("test.db"),
        driver = BundledSQLiteDriver(),
        databaseClass = AppDatabase::class,
        databaseFactory = { AppDatabaseConstructor.initialize() }
    )

    @Test
    fun migrate3To4_convertsPriority() = runTest {
        // 1. create DB with schema version 3 and insert raw data (DAOs expect latest schema!)
        helper.createDatabase(3).apply {
            execSQL("INSERT INTO tasks (id, title, is_done, created_at, priority) " +
                    "VALUES (1, 'Buy milk', 0, 0, 2)")
            close()
        }

        // 2. run migration and validate schema
        val connection = helper.runMigrationsAndValidate(4, listOf(MIGRATION_3_4))

        // 3. validate data
        connection.prepare("SELECT priority FROM tasks WHERE id = 1").use { stmt ->
            assertTrue(stmt.step())
            assertEquals("HIGH", stmt.getText(0))
        }
        connection.close()
    }
}
----

On Android (instrumented tests) the helper takes an `Instrumentation`, a database `File` and a driver, e.g. `MigrationTestHelper(instrumentation, file = context.getDatabasePath("test"), driver = AndroidSQLiteDriver(), databaseClass = AppDatabase::class)`. Also write a test that opens a database of version 1 and runs *all* migrations to the latest -- it catches gaps in the chain.

== Other important topics

=== Transactions

Several write operations that must succeed or fail *together* need a transaction:

[source,kotlin]
----
// 1) In a DAO - a function with a body
@Query("DELETE FROM tasks")
suspend fun deleteAll()

@Transaction
suspend fun replaceAll(tasks: List<TaskEntity>) {
    deleteAll()
    insertAll(tasks)
}

// 2) Anywhere - via the database object (Room 3)
database.withWriteTransaction {          // IMMEDIATE transaction
    taskDao.insert(task)
    musicDao.insertSongs(songs)
}
val found = database.withReadTransaction { taskDao.search("milk") }   // DEFERRED
----

(Room 2 on Android: `withTransaction { }` / `runInTransaction { }`.)

=== Observing changes (`Flow` and the invalidation tracker)

Each `Flow` query subscribes to the tables it reads. Any write to those tables -- through any DAO -- makes it re-query. Notes:

* Room emits even if the result did not change (another row in the table changed). Add `.distinctUntilChanged()` if needed.
* For custom reactive logic use `database.invalidationTracker.createFlow("tasks")`.
* `Flow` queries are cold: nothing runs until somebody collects.

=== Testing DAOs with an in-memory database

[source,kotlin]
----
class TaskDaoTest {
    private lateinit var db: AppDatabase

    @BeforeTest fun setUp() {
        db = Room.inMemoryDatabaseBuilder<AppDatabase>()    // desktop/iOS; Android needs a Context
            .setDriver(BundledSQLiteDriver())
            .build()
    }
    @AfterTest fun tearDown() = db.close()

    @Test fun insertAndRead() = runTest {
        val id = db.taskDao().insert(TaskEntity(title = "Test", createdAt = 0))
        assertEquals("Test", db.taskDao().getById(id)?.title)
        assertEquals(1, db.taskDao().observeAll().first().size)
    }
}
----

=== Cheat sheet: Room 2 -> Room 3

[cols="1,1",options="header"]
|===
| Room 2.x | Room 3.x
| `import androidx.room.*` | `import androidx.room3.*`
| `id("androidx.room")` + `room { }` | `id("androidx.room3")` + `room3 { }`
| `@TypeConverter(s)` | `@ColumnTypeConverter(s)`

| `runInTransaction { }` / `withTransaction { }` | `withWriteTransaction { }` / `withReadTransaction { }`
| `db.query(...)` -> `Cursor` | `useReaderConnection { it.usePrepared(sql) { stmt -> } }`

| `InvalidationTracker.Observer` | `invalidationTracker.createFlow(...)`

== Best practices and common mistakes

. *One database instance* per process; inject it.
. Keep `schemas/` in Git; review the JSON diff in pull requests like code.
. Never change an entity without bumping the version and adding a migration. Test each migration.
. Always set `defaultValue` for new `NOT NULL` columns.
. Index foreign key columns and columns used in frequent `WHERE`/`ORDER BY`.
. Prefer `@Upsert` to `REPLACE` when foreign keys with `CASCADE` exist.
. Use `@Transaction` for `@Relation` queries and for multi-step writes.
. Keep entities as a *data layer* model; map them to domain/UI models when they diverge.
. Do not use `fallbackToDestructiveMigration` for user data.
. Missing `kspXxx` configuration for a target -> "no actual"/`_Impl` errors only on that platform.
. A DAO function that is neither `suspend` nor returns `Flow` -> compile error in KMP.
